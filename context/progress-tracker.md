This keeps the spec's literal 3-part ID format (shape, timestamp, counter) intact while making cross-client collisions astronomically less likely instead of guaranteed-on-first-drop.

## Architecture Decisions

- shadcn/ui initialized with Base UI (not Radix) as the underlying primitive library — this is the CLI's current default, not an explicit choice in the spec.
- Dark theme is forced globally via a `dark` class on `<html>` in `app/layout.tsx`, since `globals.css` only defines a `.dark` override (activated by that class) and a default light `:root` — there was no toggle or existing dark theme to match, so this was the only way to satisfy "no default light styling appears."
- `proxy.ts` uses `@clerk/nextjs/server`'s `createRouteMatcher`, which this Clerk version (`@clerk/nextjs@7.7.1`) marks `@deprecated` in favor of resource-based auth checks (calling `auth.protect()` per page/route instead of centralized path matching). `03-auth.md` explicitly specifies the centralized "define public routes, protect everything else by default" pattern, which is only expressible with a route matcher, so this was implemented as specified rather than substituting the newer per-resource pattern — that would be a bigger architectural change than this unit's scope, and `createRouteMatcher` is deprecated, not removed. Flagging here since AGENTS.md says to heed deprecation notices: if Clerk removes `createRouteMatcher` in a future major version, `proxy.ts` will need auth checks moved into each page/layout/route instead.
- `lib/prisma.ts` uses Prisma 7's native `accelerateUrl` constructor option for `prisma+postgres://` URLs rather than the `@prisma/extension-accelerate` package + `withAccelerate()` extension pattern shown in some Prisma docs/skills — the extension package isn't in `05-prisma.md`'s "already installed" dependency list, and `accelerateUrl` alone is sufficient to connect through Accelerate in v7 (it's mutually exclusive with `adapter` at the type level: `PrismaClientOptionsWithAccelerate` vs. `PrismaClientOptionsWithAdapter` in `node_modules/@prisma/client/runtime/client.d.ts`). If a future unit needs Accelerate-specific features (response caching, connection metrics), that's when the extension package would actually need adding.
- `proxy.ts` now skips `auth.protect()` entirely for `/api/*` (early-return via an `isApiRoute` matcher) instead of applying the same centralized protect-everything pattern used for pages. Reason: Clerk's `auth.protect()` redirect-vs-401 decision is page-request heuristics that misfired for API routes in this Next/Clerk combination (see the 06-project-apis bugfix note above) — API routes now enforce auth themselves via `auth()` + explicit `401` JSON, which `code-standards.md` already required of route handlers regardless. This narrows, not removes, `03-auth.md`'s centralized-protection pattern: it still applies to every page route.
- `ui-context.md` documents Ghost-specific CSS variable names (e.g. `--bg-base`) and gives a few example Tailwind utility names (`bg-base`, `text-copy-primary`, `text-copy-muted`, `border-surface-border`, `text-brand`, `bg-accent-dim`) but not an exhaustive mapping. Extended that pattern consistently for the remaining tokens (e.g. `text-copy-secondary`, `text-copy-faint`, `border-surface-border-subtle`, `text-ai`/`bg-ai`, `text-ai-text`, `text-error`/`text-success`/`text-warning`). These are additive to shadcn's existing `--primary`/`--background`/etc. tokens (kept as-is for `components/ui/*` internals) — the Ghost tokens are for app-level/feature components.
- 07-wire-editor-home: `app/api/projects/route.ts`'s `GET` (owner-only list, from 06-project-apis) was intentionally *not* refactored to use the new `lib/projects.ts` helper or extended to include collaborator projects. This unit's spec said to fetch owned+shared projects "server-side using the existing project data helper" for the page itself — read as "add the helper and use it in the server component," not "change the already-shipped, already-verified API route's contract." Nothing in the app calls `GET /api/projects` over HTTP anymore (the sidebar's data comes from the layout's direct Prisma calls); if a future unit needs the API route itself to return collaborator projects too, that's a separate, explicit decision — resolving it silently as a side effect here would have violated "do not combine unrelated system boundaries in a single implementation step."
- 07-wire-editor-home: introduced `app/editor/layout.tsx` (new) as a nested layout so both `/editor` and `/editor/[projectId]` share one server-side project fetch and one client-side `EditorShell` (navbar/sidebar/dialogs) instance without duplicating either. This is the first nested layout in the app; chosen over having each page fetch and render its own copy of the chrome because layouts persist across navigations within the same segment (per Next's docs), which is what makes the sidebar/dialogs feel like a stable app shell rather than remounting on every project switch — the tradeoff (documented above under `use-project-actions.ts`) is that layout data is *not* automatically refreshed on sibling navigation, so mutations must call `router.refresh()` explicitly.
- 11-base-canvas: the spec's "error fallback for Liveblocks connection issues" is implemented via `useErrorListener` (`components/editor/canvas-room.tsx`'s `RoomConnectionGuard`), not by relying on the adjacent `ErrorBoundary` to catch it. Liveblocks' room-connection/auth failures do not throw a React render error — `ClientSideSuspense` will happily sit in its loading fallback indefinitely (retrying in the background) rather than ever rejecting into the `ErrorBoundary`. This matches the `liveblocks-best-practices` skill's own `handling-connection-errors` reference, which documents `useErrorListener` + `error.context.type === "ROOM_CONNECTION_ERROR"` as the mechanism for exactly this case, separately from the `rendering-loading-components` reference's `ErrorBoundary`+`ClientSideSuspense` pattern (which is for actual render-time errors in complex data hooks). Both are kept — they cover different failure classes.
- 08-editor-workspace-shell: superseded the previous decision above — `/editor/[roomId]` needed a structurally different top navbar (project name + share + AI toggle) than `/editor` home's (`EditorNavbar`: sidebar toggle + `UserButton` only), and Next layouts can't opt a child segment *out* of a parent layout while keeping siblings in it. Used the documented route-group pattern (`node_modules/next/dist/docs/.../route-groups.md`, "opting specific route segments into sharing a layout, while keeping others out") to split `app/editor/` into `app/editor/(home)/` (keeps the old `EditorShell` layout, URL still `/editor`) and a sibling `app/editor/[roomId]/` with its own self-contained `WorkspaceShell` (fetches its own project lists, owns its own `useProjectActions()`). Cost: `getOwnedProjects`/`getSharedProjects` are now called from two places (`(home)/layout.tsx` and `[roomId]/page.tsx`) instead of one shared layout — accepted because the alternative (threading room-specific navbar state up through `EditorShell` via context, the pattern already used for `openCreateDialog`) would have made the generic home chrome conditionally room-aware, which is a worse coupling than one duplicated data-fetch call. `app/editor/` itself has no `layout.tsx` of its own now — root layout (`app/layout.tsx`) is unaffected, so this isn't the "multiple root layouts" case the route-groups doc warns about (no full-reload-on-navigation cost).
- 18-starter-template: **`@liveblocks/react-flow`'s `onNodesChange`/`onEdgesChange` silently no-op on a `"remove"` change** — confirmed by reading `node_modules/@liveblocks/react-flow/dist/lib/flow.js`'s `applyNodeChanges`/`applyEdgeChanges` (`case "remove": break;`, for both). The only mutation that actually deletes from the room's `LiveMap`s is `onDelete({nodes, edges})` (already wired to `<ReactFlow onDelete={onDelete}>` since 11-base-canvas, for React Flow's built-in delete-selection handling). Any future unit that needs to programmatically remove nodes/edges — not just add or update them — must call `onDelete`, not construct a `"remove"` `NodeChange`/`EdgeChange`. This surfaced as a real bug during this unit's own live verification (a manually-dropped node survived a template import that was supposed to clear the canvas first) before the fix.
